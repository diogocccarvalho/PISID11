================================================================
VISAO GERAL DO SISTEMA
================================================================

O projeto é um sistema de monitorização de um labirinto em tempo
real, com sensores de temperatura, som e movimento (marsamis).

Componentes principais:
  - Simulador (mazerun.exe): gera e envia dados dos sensores via MQTT
  - Computador 1 (computer1.py): processamento e acao em tempo real
  - Computador 2 (computer2.py): persistencia no MySQL local
  - Player (player.py): estrategia de pontuacao
  - Web Dashboard (PHP): gestao das simulacoes
  - App Android: monitorizacao movel

================================================================
FLUXO DE DADOS
================================================================

1. Simulador publica via MQTT:
     pisid_mazetemp_13   -> dados de temperatura
     pisid_mazesound_13  -> dados de som
     pisid_mazemov_13    -> movimentos dos marsamis

2. Computador 1 recebe esses topicos:
     - Deteta outliers (comparacao com media dos ultimos 5 valores)
     - Guarda em MongoDB (com flag outlier=true/false)
     - Age em tempo real: liga/desliga AC, abre/fecha portas
     - Republica para PC2 via novos topicos MQTT:
         pisid_maze_data_temp
         pisid_maze_data_sound
         pisid_maze_data_motion

3. Computador 2 recebe os topicos do PC1:
     - Insere dados normais: Temperatura, Som, MedicoesPassagem
     - Insere outliers: TemperaturaOutlier, SomOutlier
     - Gera alertas na tabela Mensagens

4. Player recebe movimentos:
     - Monitoriza quantos marsamis odd/even estao em cada sala
     - Quando ha equilibrio (odd == even > 0), fecha corredores
     - Dispara Score para a cloud (max 3 vezes por sala)
     - Deteta fim de jogo e termina simulacao

================================================================
PAPEL DE CADA COMPUTADOR (RESPOSTA DIRETA)
================================================================

PC1 (computer1.py):
  - Recebe dados RAW do simulador
  - Deteta outliers
  - Guarda no MongoDB
  - Faz acoes: AcOn, AcOff, OpenAllDoor, CloseAllDoor
  - Republica dados processados para o PC2

PC2 (computer2.py):
  - So le dados (ja processados pelo PC1) via MQTT
  - Insere nas tabelas certas do MySQL local
  - Gera mensagens de alerta na tabela Mensagens
  - Publica GameStart quando deteta nova simulacao ativa

================================================================
DETECAO DE OUTLIERS
================================================================

ONDE e COMO:
  O Python (PC1) faz a deteção com este algoritmo:
  - Guarda os ultimos 5 valores validos em memoria
  - Para cada novo valor: calcula a media dos 5 anteriores
  - Se |novo_valor - media| > 5.0, e considerado outlier
  - Isso e um desvio da media com threshold fixo

NAO e Z-score a sério. Z-score real seria: Z = (x - media) / desvio_padrao
e consideraria outlier se |Z| > 3.

O SP do MySQL "Verificar_Outlier" IMPLEMENTA o Z-score real
(usa STD() do SQL), MAS NUNCA E CHAMADO em lado nenhum.
Existe no codigo como "camada de segurança extra" que ficou por ligar.

CONCLUSAO: outliers sao tratados APENAS no Python. O SP do MySQL
nao faz nada.

Verificar_Outlier  - z-score nos ultimos 5 valores — EXISTE MAS NAO E CHAMADO

================================================================
TRIGGERS
================================================================

trg_atualizar_ocupacao:
  - Dispara apos INSERT em MedicoesPassagem
  - Atualiza OcupacaoLabirinto (incrementa sala destino, decrementa sala origem)
  - RoomOrigin=0 significa largada inicial (nao decrementa)
  - RoomDestiny=0 significa marsami preso (nao incrementa)

Nota: o trigger de outlier de temperatura foi REMOVIDO porque
o Python ja faz essa separacao diretamente na insercao.

================================================================
EVENTOS DE SUPORTE SQL (PORQUE NAO FORAM USADOS)
================================================================

O MySQL tem um "Event Scheduler" que permite agendar queries SQL
para correrem automaticamente a intervalos (tipo cron job dentro
do proprio SQL). Exemplo: "corre esta query de hora a hora".

NAO foram usados porque:
  - Todo o processamento ja e feito pelo Python em tempo real
  - Os scripts Python correm em threads continuas
  - Adicionar eventos SQL seria redundante e mais dificil de debugar
  - A logica e mais clara em Python do que em SQL agendado

================================================================
LIMITES DE TEMPERATURA — ATENCAO
================================================================

Existem DOIS conjuntos de limites desconectados:

1. Cloud MySQL (setupmaze):
   normaltemperature + tolerancias -> usados pelo Python para AC e alertas
   ESTES sao os que realmente controlam o comportamento

2. MySQL local (Simulacao.limTemperaturaMax/Min):
   Definidos no dashboard web (nova_simulacao.php / alterar_simulacao.php)
   Guardados na BD mas NAO usados pelo Python
   So sao lidos pela app Android para mostrar no ecra

Ou seja: mudar os limites no dashboard web NAO afeta o simulador.

TOPICOS MQTT
================================================================

Simulador -> PC1:
  pisid_mazetemp_13     temperatura
  pisid_mazesound_13    som
  pisid_mazemov_13      movimento

PC1 -> PC2:
  pisid_maze_data_temp      temperatura processada
  pisid_maze_data_sound     som processado
  pisid_maze_data_motion    movimento processado

Controlo:
  pisid_game_control_13   GameStart / GameOver

Acoes (PC1 e Player -> Simulador):
  pisid_mazeact   AcOn, AcOff, OpenAllDoor, CloseAllDoor,
                  OpenDoor, CloseDoor, Score

================================================================
SISTEMA DE PONTUACAO (PLAYER)
================================================================

- Player monitoriza topico pisid_mazmov_13
- Controla um dicionario rooms_state: {sala: {odd, even, triggers}}
- Quando odd > 0 E odd == even numa sala -> "sala equilibrada"
- Fecha os corredores dessa sala
- Publica Score para a cloud
- Pode disparar ate 3 gatilhos por sala
- Apos esgotar gatilhos, reabre os corredores
- Fim de jogo: todos os marsamis saem (odd=even=0) ou GameOver
